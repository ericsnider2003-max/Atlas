Written for Atlas, from what has actually worked in this codebase. Every
example below is a real finding, not an illustration.

## The one idea underneath all of it

**Look for the gap between what something claims and what it does.** Not for
bugs — bugs announce themselves. The expensive failures are the ones where
everything looks right: a green test suite over unreachable code, a
"non-configurable" guarantee that config can set, a token that looks random.

Every technique below is a way of making one of those gaps mechanical.

---

## The five questions

### 1. Can anything actually reach this?

The largest finding in this codebase, by a wide margin. **96 of 145 modules
compiled, passed their tests, and could not be called from the running
program.** Every session had ended green.

*How to check:* walk the call graph from the entry point. Anything not reached
is dead, however good its tests are.

*The trap:* the first version of this check counted a config field as a
reference. `pub dictate: crate::dictate::DictateConfig` means the settings
parse, not that the code runs — `Intent::Dictate` had no arm at all. **A
detector that can be satisfied without the thing being true is worse than no
detector.**

### 2. Would this test fail if the code were wrong?

Two shapes to look for.

A test that asserts nothing passes for as long as the code compiles. A test
that asserts only `SOME_CONSTANT.contains("a phrase")` proves the wording, not
the behaviour — it is documentation with a test harness around it. There are 37
of those here and the count is pinned so it cannot grow.

*The strongest version of this check:* before writing a fix, **confirm the
proving test fails right now.** A test that already passes is testing something
else. This is one line of discipline and it is most of the value in the whole
loop.

### 3. Does the claim survive contact with the config?

Search for every place the code says "not configurable", "always" or "never",
then check the field is genuinely unreachable from YAML. A guarantee that a
`#[serde(skip)]` was quietly removed from is a guarantee that has already
failed and is still being stated.

### 4. Where are the side doors?

Ask not "can it do the bad thing" but **"can it do something that makes the bad
thing possible later"**.

A real example: Atlas could not edit `policy.rs`. But it could edit
`tests/wiring.rs` — the ratchet that catches unreachable code —
`tests/retrospective.rs` — the audit that catches bad tests — and
`config/policy.yaml`. None of those causes a mistake. **Each of them hides the
next one**, which is worse.

The fix was to fail closed: anything not known to be ordinary is a guard. **The
failure directions are not symmetric.** Over-restricting costs a question.
Under-restricting costs the limit.

### 5. What does this rest on?

Follow the chain down. Every control in the network path — loopback binding,
constant-time comparison, size ceilings, refusing to distinguish a wrong token
from a missing one — was correct and careful, and all of it rested on a token
generated by an xorshift sequence seeded with a nanosecond timestamp. It looked
like 118 bits and was determined entirely by a guessable seed.

**Careful work built on one weak assumption is not careful work.** Find the
assumption everything else takes for granted, then check it hardest.

## How to fix, once found

**Name the cause, not the symptom.** If the cause sentence is the symptom
sentence again — "it's slow" / "because it's slow" — the thinking hasn't
happened. Stop there.

**Fix where the cause is.** A change somewhere else may make the test pass, and
that is exactly what patching a symptom looks like from the inside.

**Fail rather than fall back.** When the token generator lost its entropy
source, the right behaviour was to refuse to start. A weak token generated
quietly because the good source was unavailable is worse than no token — you'd
never know, and everything downstream assumes it's strong.

**Make the fix a ratchet.** A finding fixed once comes back. A finding turned
into a test that fails the build cannot.

---

## What this can't do

These catch structural failures, not wrong logic. A test can assert something
and still assert the wrong thing. A module can be reachable and useless.

That's what review by a person or a model is for — but it now only has to look
at what these can't see, which is a much smaller surface.

## The uncomfortable part

Every finding above was in code that had been written carefully, reviewed, and
was passing 2,000 tests. **Care is not a substitute for a check.** The reason
to make each of these mechanical is not that the work was sloppy — it's that
this class of failure is invisible to the person who wrote it, by definition.
