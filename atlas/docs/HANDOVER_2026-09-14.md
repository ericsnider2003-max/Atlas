## The headline: the full test suite runs now

Every previous session in this chat carried the same standing caution —
*"this sandbox's disk is the binding constraint on getting real `cargo test`
numbers for the full tree; the personal-island tool is the reliable
workaround, not a full substitute."* That is no longer true. This
environment linked every test binary in the tree without trouble.

The first thing a full run said was that **18 tests were failing in the tree
that was handed over**, across 8 binaries. None of them were new. They had
simply never all been run at once.

That is worth sitting with, because it is the project's own named pattern
turned on the tooling rather than the code: *a detector that cannot run is
not a detector.* The island approach was honest about being partial, and it
was still the reason a whole class of defect stayed invisible for days.

**Baseline before this session: 4,116 passing, 18 failing** (4,134 tests
across 198 binaries).
**Now: 4,244 passing, 0 failing**, across 208 binaries — 110 of those tests
are new this session.

Anything that follows about "verified" now means the whole suite, not a
slice of it.

## 1. The 18 failures, and what caused them

### The shipped config had almost every feature switched off

Fourteen of the eighteen were one bug. `config/tools.yaml` — the file a real
install actually runs on — contained **84 `enabled: false` lines and exactly
one `true`**. Research, notifications, panels, the clipboard, the hub, the
quick-input surface, the returning brief, the daily digest, file access,
the working set and eight more were all off in the file, against code whose
own `Default` impls say each of them is on unless you turn it off, and
against tests elsewhere in the suite asserting exactly that.

The one `true` was `backup.enabled`, and the reason it was the one is the
whole story: it was caught by hand during the 12–13 Sep reconciliation,
because that single test happened to be in a slice that could be run. The
other 83 were the same bug and nothing could see them.

**Fixed:** 20 flags set true — the 18 whose struct `Default` is on, plus
`research` and the top-level `enabled`, which the settings registry
declares on. Everything genuinely opt-in (`kin`, `phone`, `vault`,
`finance`, `remote`, `cloud`, `ios`, `android`, `mesh`, `presence`,
`vision`, `gaze`, `ocr`, `voice_id`, `proactive`, `server`, `dictate`,
`budget`, `overnight`, `identity`, `opsec`, …) was left off.

**Guarded:** new `tests/shipped_config.rs`. It compares every `enabled` flag
in the shipped file against the code's own default and fails on any that
ships off against a default of on, unless it is named in a
`DELIBERATELY_OFF` list with a reason. The list is empty. Turning something
off in the shipped file is now a decision someone writes down.

That test was written *before* the fix and watched to fail, naming all 18.

A third test in the same file turned up a related mess: **two places
declared a default and disagreed.** `settings.rs`'s registry hardcoded a
default per key, beside each live value, so the hub could show "changed from
default"; each config struct declared its own `Default` separately. Nothing
made them agree and three had drifted apart. **Now fixed — see section 2.**

### Two stale opsec tests

`tests/opsec_recovery_undo.rs`'s first two tests predate `opsec.rs`'s split
of its word lists into unambiguous and ambiguous — the fix the main chat
made independently and the reconciliation kept. They passed `"I deploy next
month"` and `"outside the hangar"` bare and expected a hit, which under the
split is precisely the false positive the split exists to stop: "deploy" is
what a developer does to a server on an ordinary Tuesday.

`tests/opsec.rs` specifies the current design in full and passes. Those two
were simply never updated with it.

**Fixed:** both rewritten around the current design, each keeping what it
was really testing (movement caught, place caught, each risk's `fix()` says
the useful thing) and each gaining the negative half — the bare sentence
finding nothing — so the split is guarded there too.

### Documentation drift (found before the above, in the first run)

`bug_sweep`'s `STALE_DOC_CLAIMS` ratchet was at 7 and the tree measured 10.
Two of the three new offenders were in `MODULE_REFERENCE_2026-09-13.md` —
a programmatically-generated dump of every module's own doc comment, which
is the exact file the guard already had an exemption for, pinned to the
previous day's filename. An exemption that expires the moment the file it
describes is regenerated is not an exemption; it is a delayed failure.

**Fixed:** exemption matched by `MODULE_REFERENCE_` prefix rather than exact
date, since the property that earns it is how the file is produced. The
third offender was one sentence in `OUTSTANDING_TASKS_2026-09-13.md` that
happened to contain the word "timing"; reworded. Ratchet stays at 7.

## 2. One place declares a default, not two

Eric's ruling: the feature's own code wins.

`settings.rs`'s `registry()` built each hub entry with the live value read
out of the config *and a default typed in beside it by hand*. Each config
struct also declared its own `Default`. Nothing compared the two, and three
had drifted: `voice.enabled` and `research.enabled` were written `true` in
the registry against `Default` impls saying false, and
`models.memory_budget_mb` was 3500 against a struct default of 6000. So the
hub's "changed from default" marker was wrong about three settings, and a
person reading the hub and a person reading the code got different answers
to the same question.

**The fix removes the second answer rather than adding a test that the two
answers match.** `registry()` now builds the list twice — once against your
config, once against `ToolsConfig::default()` — and takes each item's
default from the second. Every hand-written default is gone: `toggle()` lost
its `default_on` parameter (48 call sites) and the seven inline `Setting`
literals carry placeholders that get overwritten. There is nowhere left to
write a default that can disagree with the code.

**Consequences, which are real and worth knowing:**

- **Research and voice now ship off.** Their own code says off; the shipped
  config followed the registry's `true` and now follows the code. Research
  is the only thing in this tree that leaves the machine, so waiting to be
  asked for is the right default anyway — but it *is* a change: turn it on
  once in the hub. Everything underneath (the DuckDuckGo search tool, the
  headless-Chrome fetch tool) stays configured, and a test asserts it, so
  the switch works the moment you flip it rather than handing you a control
  that does nothing.
- **`models.memory_budget_mb` stays at 3500** in the shipped file against a
  struct default of 6000, recorded as a deliberate difference with the
  reason (6000MB of model on an 8GB machine leaves the rest of the system
  fighting for what's left). Which of the two numbers is the right *default*
  is now a small, concrete open question rather than a silent contradiction.
- Four tests that leaned on research being on in the shipped file were
  rewritten. Two were about the shipped default and now assert the new one;
  two were about the daemon's failure messages and had no business
  depending on a config default at all — they turn research on themselves
  now. That dependency is exactly why a default change made the *daemon*
  look broken.

**Guarded, and the guard had a hole.** `tests/shipped_config.rs` asserts
that the registry, handed the default config, reports nothing as changed.
Deliberately breaking the derivation did not fail that test — because with
the derivation gone every default equals its own value, so nothing is *ever*
changed and both that test and the hub's markers would go permanently blank
while the suite stayed green. A second, positive test now takes a config
that differs from the default in exactly one known place and asserts it is
reported that way, by name.

## 3. `atlas share` carries files now

Eric's ruling: build the file half.

```
atlas share "here's the draft" --file report.pdf --to Priya
atlas handoffs list      #  1  from Priya — the report (report.pdf, 200 KB, not opened)
atlas handoffs keep 1    #  moves it into the tray. This is the moment Atlas may read it.
atlas handoffs drop 1    #  bins it, bytes and all
```

The covering line is optional when there's a file — `--file report.pdf --to
Priya` is a complete sentence, and requiring words as well would just get
"here" every time.

**The three sub-decisions, settled and asserted rather than only written
down:**

- **Size cap: 8MB**, deliberately below the tray's own 20MB. base64 inflates
  by 4/3, so 8MB of file is ~10.7MB on the wire and the whole body is read
  into memory by a listener that services one connection at a time; and this
  arrives *unasked*, which deserves a tighter bound than something you handed
  Atlas yourself. Over it, the sender is told to put the file somewhere and
  send the link. A test asserts the peer cap is the smaller of the two, since
  that relation is the actual decision.
- **Where the bytes land: a `handoffs/` doorstep folder**, never the tray
  folder. Same reasoning as notes — the tray is what Atlas reads.
- **May Atlas open it: no.** Not on arrival, not to list it. `handoffs list`
  shows the name, the size and who from, and says "not opened". `keep` is
  what moves it into the tray, and from there the tray's normal rules apply.

Three more things that came out of building it:

- **The filename is the most dangerous field in the feature** — a string
  chosen by the sender, about to be turned into a path. It goes through
  `tray::safe_name` at the door, not at whichever call site eventually
  writes it: there is one door and there will be more than one call site. A
  test throws `../../etc/passwd` and Windows-shaped equivalents at it and
  asserts what actually got written stays under the doorstep folder.
- **The listener's body cap had to become per-endpoint.** It was a flat 4096
  bytes for everything, which is right for a signal and made a file handoff
  silently impossible — truncated to 4KB, then failing to parse. Raising it
  for everything would be the wrong fix: a peer-reachable endpoint with a
  large body cap is a memory-exhaustion surface and `/signal` has no use for
  one. The cap is chosen from the request line before a byte of body is
  read, and the `/handoff` bound is computed from the file cap rather than
  guessed.
- **A body that claims a file and doesn't decode is refused outright**,
  rather than delivered as a bare note. Half a file looks exactly like a
  whole one on a list, and the covering line would still read fine.

The file round trip gets its own real-socket test rather than trusting the
note one — that test is what caught the note sender putting its token in the
body instead of the header, and a file adds base64, a much larger body, and
the new cap.

## 4. `returning.rs` — welcome() and full_brief() wired for real

Green-lit by Eric. This was named in the 13 Sep handover as needing a
decision because it meant restructuring a live, tested path.

**What was wrong.** `welcome()` (the Straight/Offer/Nothing decision, tiered
by how long you were away) and `full_brief()` (the answer to yes on an
offered brief) were complete, tested and unreachable. The away path in
`daemon.rs` predated `returning.rs` and built a pre-formatted string —
`Journal::brief` for what Atlas did, `notify::spoken` for what could not
reach you, concatenated — so nothing in the running program ever had the
`[Happened]` list those two functions take. Two of `welcome`'s own
decisions were separately reimplemented inline at the call site.

**What it does now.** `Daemon::happened_while_away` merges the journal and
the outbox into one time-ordered `[Happened]` list; `welcome()` decides what
to say about it; the panel shows the same list rather than a separate
assembly that could drift from what was said out loud. An `Offer` holds the
list in `pending_brief_detail`, and a bare yes on the next turn runs
`full_brief()` against *that* list rather than a journal that has moved on.

Five decisions worth knowing, each of which came out of building it:

- **The offer is deliberately not routed through `Pending::Clarification`.**
  That machinery parks a question and treats your next utterance as its
  answer — the opposite of what "when you're ready" promises. The offer
  rides along on a reply you asked for, and you may well have come back to
  do something specific. A bare yes is checked last, below every other
  pending answer.
- **A yes only resolves an offer that was actually delivered.** Both halves
  are set on the same turn; without the check, saying "yes" as the first
  thing after an absence would answer an offer you had not heard.
- **`welcome` calls a sub-`away_after` absence no absence at all.** Right
  about the journal, wrong about the outbox — something held back *because*
  you were not there is owed either way, and `away_after` is configurable
  low enough for the two to disagree. Held things are still said.
- **The "While you were away" framing is restored when no address is set.**
  `welcome` leans on the greeting to say "you have just come back", and the
  default address is deliberately nothing at all. Without it, "Disk is
  nearly full." is indistinguishable from something happening right now,
  which is the entire point of a returning brief. Done in `daemon.rs`, not
  `returning.rs`: being on the return path is the daemon's knowledge.
- **A spoken address change beats the config file**, and the check is
  `store.exists("address")` rather than the loaded value — `Address::None`
  is both "never asked" and what "stop calling me that" deliberately
  writes, and treating the second as the first would let a config file undo
  it on the next restart. As a side effect `returning.address` in
  `tools.yaml` now works at all; previously only the spoken one was read.

**A bug caught while proving the tests could fail.** The first version
excluded only `Upkeep` from the journal, which let `Kind::Asked` through —
a verbatim record of what *you* said. Coming back produced *"I've got an
update on call me boss when you're ready."* Your own instruction from before
you left, recited back as news. The filter is now an exhaustive match
stating positively which kinds reach a brief (`Published`, `Scheduled`,
`Blocked`) and why each of the others does not — including `Offered`, which
would double-report anything already held in the outbox.

**Tests:** `tests/returning_wired.rs`, 16 tests. Every one was deliberately
broken and watched to fail before being trusted — nine separate breaks.
Two could not fail on the first attempt and were rewritten:

- the address test asserted `contains("boss")` and passed with the address
  wiring disabled, because the journal was reciting "call me boss" back;
  narrowed to the greeting specifically. That is the bug above, caught by
  the break rather than the test.
- the `needs_you` test recorded its `Blocked` event with `ok: false`, so
  `failed` carried it and `needs_you` was never under test.

## 5. `household::share_with_friend` wired over the peer channel

Eric's ruling: a note, over `kin.rs`'s existing peer channel, rather than a
portable file bundle.

**What was wrong.** `share_with_friend` built a `Handoff` — one-way, a note
or file, carrying nothing about your household — and nothing sent it. It was
the last piece of that cluster still unwired after the device-pairing round.

**What it does now.**

```
atlas share "<the note>" --to <Friend>      # send
atlas handoffs list                          # what friends have sent you
atlas handoffs keep <id>                     # take one into the tray
atlas handoffs drop <id>                     # bin it
```

The transport reuses the pairing you already have (`atlas invite` / `atlas
accept` filled in the contact list). `kin::send_handoff` posts to a new
`/handoff` endpoint over `http::post_json`.

**Where a note lands, and why not the tray.** The ruling settled the
transport; it did not settle the destination, and the obvious answer is
wrong. The tray's own rule is that handing Atlas something says "look at
this", and Atlas then goes and reads it — right for something you sent from
your own phone, wrong for something that arrived unasked, because a link is
a fetch and it would mean a peer credential could make your Atlas go and
retrieve a URL. "A friend I paired with" is not the same trust as "me, from
my other device".

So a note waits in `household::Inbox` as text in a list. `atlas handoffs
keep` is the deliberate act that moves it into the tray, and *that* act, not
the arrival, is what lets Atlas look at it.

**The structural separation is kept, not bent.** `kin::Incoming` has exactly
one thing it may become — a nudge — and `tests/guards.rs` fails the build if
a second path appears. Rather than smuggle content through the type that is
already spoken for, content gets its own type (`kin::Delivered`), its own
endpoint (`route_handoff`, which shares no code path with `route_signal`),
and its own single destination (`kin::as_waiting`, into the inbox and
nowhere else). Three new `tests/guards.rs` entries hold that line the same
way the signal one does.

Other decisions:

- **Notes are rate-limited on their own counter**, cap 10 per hour against
  signals' 3. Sharing one bucket would mean three notes from a friend
  blocking their next *urgent* signal for an hour, which is the wrong
  failure: a signal interrupts you, a note waits in a list.
- **The sender's claimed name is ignored.** A body is a claim; a token is
  not. The name recorded is the one you gave that peer when you paired —
  otherwise a paired friend could make a note appear to come from your
  accountant.
- **Notes are free text**, so the sender JSON-escapes properly. Pasting a
  note straight into a body either breaks the parse or lets the note's own
  content close a field and open another.
- **The waiting list is bounded** at 100, oldest dropped: a peer that has
  gone wrong fills a list rather than a disk.
- **`carries_history: true` is refused at the last point before the bytes
  leave the machine**, even though `share_with_friend` hard-codes false.

**A duplication found and removed while wiring.** `SignalListener::
handle_one` parsed the body and called the door itself, which meant two
implementations of the same routing: `route_signal`, tested directly, and
this copy, which is the one a real peer actually reaches. Two copies of a
security boundary is one too many — a rule added to one and forgotten in the
other looks exactly like a rule that is enforced. `handle_one` now routes
through the functions and is only the socket.

**Tests:** `tests/handing_to_a_friend.rs` (16) and three additions to
`tests/signal_listener.rs` covering the real socket. Five deliberate breaks
watched to fail, plus one on the new guards entry.

## 7. Fitting a new machine: `adapt.rs` wired, and a cross-platform bug it uncovered

This one matters more than a routine wiring pass because of the stated goal
— friends running their own Atlas on their own hardware.

`adapt.rs` describes a two-layer config split: `config/*.yaml` is the recipe
that ships to anyone and uses `%LOCALAPPDATA%` placeholders, and
`config/machine.yaml` is what Atlas found on *this* computer and is never
shared. Every function was written and tested. **Nothing ever wrote the
second file and nothing ever read it**, so in practice there was one layer,
the shipped one, carrying a literal `C:/Program Files/Google/Chrome/...` and
a Realtek microphone name.

Now wired:

```
atlas adapt           # look around, write config/machine.yaml
atlas adapt show      # what it found, and whether the displays have changed since
atlas adapt fixture   # monitor geometry as a test fixture, matching the real desk
```

`Config::load` applies the machine layer over the generic one, deliberately
in one place rather than at each call site — a config that is only correct
if you remember to correct it is the shape of bug the split exists to
remove. No machine file is the normal case (a fresh clone, and every test in
this tree) and means the generic layer stands unchanged.

How an app gets found is worth one line: take the generic guess, expand its
`%VARS%`, and check whether that is really a file here; if not, look for the
bare executable on `PATH`. The fallback is what makes a Linux or macOS
machine work at all, since a Windows `C:/Program Files/...` guess is never
going to resolve on one.

**`leaks_a_username` is now a real test** over every shipped config file,
which is the concrete form of "you can hand this to a friend". It passes
today — this is a guard, not a bug found. It exists because that is how a
personal path ships: not by anyone deciding to, but by nobody looking.

### The bug underneath: mic detection had never run off Windows

The outstanding-task list said "microphone enumeration is unimplemented;
`audio::parse_devices` is correct and no OS command calls it". Half of that
was wrong, and the wrong half was the dangerous one. A command *did* call
it — `probe_devices`, from `voice_loop`, on every start — hardcoded to
`ffmpeg -f dshow`, which is Windows-only. On Linux and macOS it fails,
`voice_loop` prints "couldn't list audio devices" and falls back to the
device name in `tools.yaml`, which is a *Windows* device name, so that fails
too. **Mic auto-detection — the whole point of which is not trusting that
guess — had never once run anywhere but Windows.**

Fixed by making the enumeration ask each platform the question it answers:
`-sources alsa` on Linux, `-f avfoundation` on macOS, dshow on Windows, with
a parser for each. `firstrun`'s setup wizard also reported zero microphones
with a comment saying enumeration didn't exist; it asks for real now.

Two bugs of my own, caught by tests written before the fix:

- The macOS parser stripped ffmpeg's line prefix using the *last* `]`, which
  ate the device's own index and left a line that no longer looked like a
  device. It found nothing, on the platform that has no other way to be
  checked from here.
- `looks_builtin`'s hints were written for Windows device names, so ALSA's
  `HDA Intel PCH` — the onboard audio on most laptops — was not recognised
  as built in. That is the classification that decides whether Atlas grabs a
  Bluetooth mic and collapses the audio you were listening to, which is the
  one thing `audio.rs`'s module doc says it exists to prevent.

What is verified here: the command chosen per platform, all three listing
formats, and a real `ffmpeg` run on this machine (which correctly reports no
devices — this container has none, and `null`, ffmpeg's discard device, is
refused rather than offered as a microphone that records silence). What is
not: byte-exact names from hardware that exists. That stays hardware-blocked.

`DEAD_CAPABILITY_CEILING` 287 → 292, with the five named individually — four
of them are platform parsers that only `probe` calls, and the fifth flipped
purely because a stale comment naming it was deleted. The alternative,
making them private, would cost the Windows and macOS parsers their direct
tests. Written up in `tests/bug_sweep.rs`.

`docs/MODULE_REFERENCE_2026-09-14.md` regenerated, and the generator kept at
`docs/genref.py` so the next one is a re-run. It now takes wiring from
`tests/wiring.rs`'s own list instead of recomputing it — the previous
edition used a looser rule and reported a number that test would not have
agreed with.

## 8. Updating is not reinstalling — `atlas update`, and the evidence for it

The objection was specific: not enough evidence to justify deleting and
reinstalling several times to try things out. That is the right instinct
about the wrong situation. Updating Atlas should never have meant deleting
it — but nothing said so, nothing checked it, and there was nothing to point
at.

```
atlas update
```

prints, by name, every file an update would replace and every file it would
leave alone, and says whether it is safe. It moves nothing. It is a report
you read *before* doing anything, which is the difference between believing
an update is safe and having looked.

The arrangement it reports on:

| | what | what an update does |
|---|---|---|
| the program | the `atlas` binary | replaced — this *is* the update |
| the recipe | `config/*.yaml` | replaced when the shipped recipe changed |
| your machine and its memory | `config/machine.yaml`, `data/` | untouched |

So an update is: stop Atlas, rename the binary to `atlas-<version>.previous`,
drop the new one in, start it. The `.previous` copy is the way back without a
download, and it is named by version so two updates in a row don't lose the
one that worked.

**The evidence, since that was the actual ask.**
`tests/updating_without_reinstalling.rs` builds an install with notes, a
vault, peer tokens, backups and logs in it, runs a real update over the top —
actually overwriting the shipped config and the binary — and then checks
every one of those files byte for byte. It also asserts the two lists never
overlap, because that disjointness is the only thing the whole arrangement
rests on, and separately that the shipped config really *was* replaced (a
test that only checks nothing was lost would pass on an update that did
nothing).

There is also now a `.gitignore`, which the repo did not have. `data/` and
`config/machine.yaml` were previously committable, which is half of why a new
copy felt like it would tread on the old one.

Breaking the guarantees deliberately: dropping `data/state` from the keep
list fails, `safe()` ignoring at-risk items fails, an unversioned `.previous`
name fails. One did **not** fail on the first attempt — the branch that
reports a file as at-risk cannot fire against the real lists, because a test
asserts those lists stay disjoint. A branch guarding an invariant that keeps
it from ever running is precisely what this project keeps finding, so it was
made reachable (`check_with` takes the lists) and is now exercised with
deliberately overlapping ones.

`docs/INSTALLING.md` is new and separates the two jobs. `docs/FIRST_BOOT.md`
is marked superseded and kept for its Windows ambushes — its step 3 was a
page of PowerShell for reading app paths and monitor geometry by hand and
pasting the numbers into `fake_monitors()` in `src/main.rs`. `atlas adapt`
does that now, so editing source to record a monitor layout is no longer a
step anyone should take.

## 9. The dead-capability list, finalized

The ceiling was a single number that could only shrink. It did its job and
then stopped being informative: "292" says something is wrong somewhere and
nothing about what, so every encounter with it ended in reading a
justification and moving the number. A smoke alarm, not a diagnosis.

**First, the number was wrong.** The sweep read `src/` non-recursively, so
`src/market/` and `src/platform/` were invisible in both directions — three
functions were counted dead *while being called* from those directories, and
nineteen dead ones inside them were never counted. It also matched callers by
plain substring, so any function whose name is a suffix of another's counted
as called by its sibling: `vault::seal_bytes` was hidden behind
`vault::unseal_bytes`, and twelve were hidden that way in total. Modules were
keyed by file stem too, which silently merged `src/levels.rs` with
`src/market/levels.rs` and `src/session.rs` with `src/market/session.rs`.

Fixing all three took the true count from 292 to 318. **Twenty-six functions
were dead the whole time and could not be seen.**

**Then the list was made a list.** `tests/dead_capabilities.rs` splits the
same set four ways, because they are not the same problem:

| group | count | what it means |
|---|---|---|
| orphan | 9 | nothing calls it. Not production, not its own module, not a test. |
| test-only | ~147 | a real capability with a test and no production caller. The backlog. |
| helper, also tested | ~122 | called only inside its own module, tested directly. Fine. |
| helper, untested | ~29 | called only inside its own module, no test. Should mostly be private. |

The nine orphans are **named individually with what each is waiting on**, and
a new one fails the build by name rather than by a count going up. A second
test rejects an orphan listed without a real explanation, so the list cannot
decay into names.

Acted on in the same pass:

- **`vault::seal_for_real` and `unseal_for_real` deleted.** Windows DPAPI
  wrappers taking the passphrase as `&str` — a signature that, by their own
  replacement's documentation, is why they were never called: the vault holds
  a derived key, not the passphrase. Two functions for one job, one
  documented as unusable, both named `_for_real` while the real path is
  `seal_aead`. That naming is a trap in a file that has already shipped a
  crypto mistake once.
- **`index::default_roots` wired**, and it turned out to be the same
  cross-platform bug as the microphone one. The shipped allowlist is
  `%USERPROFILE%/Desktop` — a Windows environment variable. On Linux and
  macOS nothing sets it, the paths don't exist, and **file indexing had zero
  usable roots with no error anywhere.** It now falls back to the real home
  directory, but only when *none* of the configured roots resolve, because
  this is an allowlist and widening one quietly is the thing that must not
  happen.

One guard did not fail when broken: making the sweep stop descending into
subdirectories left everything green, because its assertion is
`count <= ceiling` and a detector that suddenly sees *less* passes happily.
A ratchet cannot catch its own detector regressing. Both the recursive walk
and the whole-word matcher are now named in `tests/guards.rs`.

## 10. The voice input path: it stops when you stop

`endpoint.rs` has known when a person has finished speaking since the day it
was written. Its own doc opens: *"Recording for a fixed eight seconds is the
most-copied mistake in voice software. It cuts you off mid-word when you have
more to say, and makes you wait seven seconds after 'yes'."* And then
`config/tools.yaml`'s record command carried `-t {seconds}`, so every turn
recorded for eight seconds regardless — because **nothing ever produced the
windows of audio the endpointer decides from.**

That missing half is now three small pieces, all in-house:

- `audio::level_db` — RMS over raw 16-bit PCM, in dBFS. No dependency; a
  decoder is not needed for audio this program specified the format of.
- `audio::wav_bytes` — the forty-four byte header whisper needs afterwards.
- `audio::stream_args` — ffmpeg streaming raw PCM to stdout with **no `-t`**,
  so the recording runs until Atlas stops it.

`Voice::listen_until_you_stop` reads that stream a 250ms window at a time,
measures each window, hands the number to `Endpointer`, and kills the child
when it says you are finished. `Voice::listen` tries it first and falls
through to the old fixed path on any problem — tried there rather than at
each call site so the daemon loop, the console loop and the wake-word path
all get it without a signature change.

**An honest limitation, measured rather than assumed.** RMS rather than peak
is what stops a keystroke reading as a shout: one full-scale sample in a
250ms window is 0 dBFS by peak and **−36 dBFS by RMS**. But the shipped
threshold is −38, so −36 still clears it. The correct word is *attenuated*,
not *eliminated* — RMS buys 36 dB and the last two are not there. What it
costs is bounded: a lone click cannot end a turn, only reset the silence
timer, so the worst case is one extra pause of waiting. Whether −38 is right
against a real desk is a tuning question that needs real audio.

### Which ear it listens with

`hearing.rs` was complete, tested and unreachable, and part of why is worth
recording: it needs a list of the machine's audio devices, and device listing
was hardcoded to Windows `dshow` until earlier today.

What stood in for it was `audio::choose`, which picks on the device's *name* —
does it look built in, does it look like a headset. That is a guess about
hardware from a string, and the case it gets wrong is the one Eric actually
has: a laptop shut on a stand behind two monitors has the most built-in-looking
name there is and cannot hear you.

`hearing` measures instead. It records a second from each candidate, reads the
level back through `volumedetect`, and remembers the answer across runs so the
measuring happens rarely. It also refuses to pay the Bluetooth cost when it
buys nothing — opening an AirPods microphone drops the link to a headset
profile and wrecks whatever you were listening to, and at a desk with a webcam
that hears you, that buys nothing.

Where Atlas does **not** have a signal, it says so rather than inventing one:
`phone_active` and `audio_playing` are false because nothing reports them, and
`presence_unknown` is set honestly when the monitors cannot be read. That
field exists because the module already knew the difference between "no" and
"don't know".

### What is blocked

The loop has never read a byte from a real microphone — this container has no
sound hardware. Everything above is arithmetic on bytes and is proven; the
live behaviour is not, and the −38 threshold wants one real session to
confirm.

`nudge`'s proactive behaviours were the next track and one of them turned out
to be blocked behind something bigger: `nudge::drifted` needs a
`contents::Contents`, and **nothing in the program ever builds one**.
`contents.rs` is nominally wired — `contents::drift` even has a guard entry —
but its central type is never constructed, so the drift it detects cannot
occur. That is a feature to build, not a wire to connect, and it is named as
such rather than faked.

## 13. The notes index: `contents.rs` and `nudge::drifted`, built and wired

### What was actually wrong

`contents.rs` was one of the cleanest modules in the tree. A `Line`, a rule
for what makes a line worth reading (`is_useful` — a line that restates the
filename tells you nothing the directory listing didn't), a search over an
index (`what_to_open`), a drift check (`drift`), a boot report (`boot`). All
of it tested, in `tests/contents_trace_voice.rs`, against hand-built
`Contents` values.

**Nothing in the program ever built a `Contents` from a folder.**

That is the whole failure, and it is worth being precise about its shape
because it is subtler than the usual hollow module. `contents.rs` was
*nominally wired* — `contents::drift` even had a `tests/guards.rs` entry
saying what breaks without it. But an index nothing writes cannot drift, so:

- `drift` compared a thing that was never constructed against a folder,
- `nudge::drifted` had no `Drift` to be given and no caller,
- `nudge::what_i_know_of` had no `Contents` to report on and was a named
  orphan in `tests/dead_capabilities.rs`,
- `what_to_open` was on the built-but-never-called list.

Four functions across two modules, every one of them green, and the feature
did not exist. The previous session's outstanding list called this "blocked
behind something bigger" and named the prerequisite correctly: *the missing
half is a feature, not a wire.*

### The half that was missing

Appended to `contents.rs`, under a divider that says exactly this:

| Function | What it does |
|---|---|
| `names_on_disk(dir)` | what is actually in the folder, by the names an index uses — note stems and sub-folder names, nothing else |
| `says_for(text)` | what a note is about, from the note itself |
| `line_for` / `line_for_folder` | one line, read off disk |
| `from_folder(dir)` | **the function whose absence made everything above unreachable** |
| `parse(folder, md)` | the inverse of `as_markdown` |
| `save` / `load` | the master index, written down and read back |
| `rebuild(dir)` | from_folder + save — what the nudge offers to do |
| `master_path(notes_dir)` | where it lives |
| `MASTER_FILE`, `HEADER`, `MAX_SAYS_CHARS` | the file's name, its do-not-hand-edit header, the length past which a line stops being scannable |

Four decisions in there are load-bearing:

**The index lives beside the folder, not inside it** — `data/index.md` for
`data/notes`. Inside, it would be the one file you have to list the folder to
find, and the folder is what it exists to save you listing. It also cannot
then index itself. (`names_on_disk` skips a copy left inside anyway, because
"cannot happen" and "is not checked" are different things.)

**It is written once and read back, never re-derived.** This is the decision
the whole feature turns on. A `load_index` that rebuilt from the folder would
agree with the folder *by construction*: it could never be wrong, so the drift
check would silently stop meaning anything while every test stayed green. The
first build is silent (a folder that has never been indexed disagrees with
nothing); every build after that is one Eric asked for.

**A note with no prose gets an empty line, not its title.** Falling back to
the filename would be the exact thing `is_useful` rejects, and it would defeat
`useless_lines()` — the check that finds notes the index cannot actually help
you find. A rebuild now says how many it could not summarise.

**The summary is one sentence, capped at 110 characters, cut at a word
boundary, and never carries a newline.** The last of those is not cosmetic:
the file format is one line per item, so a description with a line break in it
writes a file that does not parse back — and an index that does not parse back
reads as drift that never happened.

### Wired

`Daemon` gained `contents` (the master index; `index` on that struct is the
*file* index, an unrelated thing), `load_index`, `index_drift`,
`rebuild_index`, `notes_dir` (one reader, so the library and the index can
never end up looking at two different folders), and `index_drifted` — what
the last check found, waiting to be raised.

The check runs hourly, **above** the speak gate, because noticing and saying
are two different things: a drift found while Atlas is in focus mode belongs
in the log, and a check that only ran on the ticks Atlas may speak would go
unrun for an entire focus session. The raise happens **last** in the tick,
after `nudger.consider` and `proactive.consider` have had their turn, and only
if nothing else took the floor. A stale index is a real fault; it is never the
most urgent thing in the room, and two questions asked in one tick means one
of them gets the answer meant for the other.

It goes through `may_raise`/`raised` like every other nudge, so declining it
sticks and silence widens the gap.

### The part that would otherwise have been theatre

`proactive::from_nudge` puts a nudge's `relief` in front of you as the command
that runs if you say yes. `nudge::drifted`'s relief is the string
`"rebuilding the index"`. If that text parses to `Intent::Unknown`, saying yes
to the offer agrees to **nothing happening** — which is precisely the failure
this codebase already names for `confirmed.rs`.

So the wiring is not just a call site. It is:

- `Intent::RebuildIndex` and `Intent::WhatIHave(String)` in `intent.rs`,
- both phrase sets in `config/commands.yaml`, with `"rebuilding the index"`
  listed **first and verbatim**,
- their places in the six exhaustive matches the compiler found
  (`connectivity`, `categories`, `policy`, `session`, `brain`, `daemon`),
- dispatch in `Daemon::execute_inner`,
- `atlas index [status|show|rebuild]` for the same thing outside the daemon.

`tests/knowing_the_map.rs` asserts the round trip end to end: take the nudge,
turn it into an offer, hand the offer's own command to the real parser, and
require `Intent::RebuildIndex`.

`RebuildIndex` is `ProceedAndReport`, not `AutoProceed`. It rewrites a file
Atlas wrote and changes none of the notes — but an index that changes under
you without a word is how a trusted map goes wrong unnoticed.

### One doc claim corrected rather than satisfied

`nudge::what_i_know_of`'s own doc said it was "reached from the daypart brief
because the daypart brief is the first thing Atlas does on any given
morning". It was reached from nowhere. Given callers, the daypart greeting
turned out to be the **wrong** home: a morning greeting that recites an
inventory count every day is a notification, which is the thing the module is
written against. It is reached instead from the two moments where the count is
an answer rather than an announcement — being asked what Atlas has written
down, and having just rebuilt. The doc now says that, including that it used
to say something untrue.

### The bug the round-trip test found

`as_markdown` writes a note with no summary as `- blank — ` with a trailing
space. `parse` trimmed the line and split on `" — "`, which no longer
matched — so the line was dropped, and a note with a blank summary came back
as a note that had **vanished**. Drift that never happened, reported by the
one file that must never be wrong about that. Caught by asserting
`parse(as_markdown(x)) == x` over an index containing a blank line, a
sub-folder and an ordinary note.

### Every new guard was watched failing

Fourteen deliberate mutations, each reverted after: summaries falling back to
the title, truncation removed, sentence-cutting removed, the empty-summary
parse branch removed, every bullet taken as an index line, `names_on_disk`
counting anything, the index listing itself, the master file written inside
the folder, sub-folders ignored, **the index re-derived instead of loaded**,
the rebuild reporting the state it just created, blank summaries going
unmentioned, the relief phrase removed from the command config, and the first
index never written down.

Twelve were caught first time. Two were not, and both misses were worth more
than the twelve:

1. **The re-derived-index mutation passed every test.** Every daemon test in
   the file started with *no* index, so the load branch — the ordinary case in
   real use, where Atlas was off and the folder moved on without it — was
   never the thing under test. Added
   `a_daemon_that_starts_with_an_index_already_there_reads_it_rather_than_rebuilding`.
2. **The `config/commands.yaml` guard passed on its own comment.** The needle
   was `rebuilding the index`, and the comment above the line quotes the
   phrase. Removing the phrase itself left the comment, and the guard agreed.
   The needle is now `"rebuilding the index",` with the trailing comma, and
   the consequence text says why the comma is load-bearing. This is the same
   failure `tests/bug_sweep.rs` fixed last session — prose about dead code
   making the code look alive — in a different file, found the same way.

### Ratchets

- `tests/new_capabilities_are_wired.rs`: `contents::what_to_open` and
  `nudge::drifted` removed from `KNOWN`.
- `tests/dead_capabilities.rs`: `nudge::what_i_know_of` removed from
  `ORPHANS`. **Named orphans 11 → 10.** (Section 12 and the 09-14 task list
  both said "nine"; the list has eleven entries and the prose was counting the
  bullet groups, not the names. Measured, not retyped, from here on.)
- `DEAD_CAPABILITY_CEILING` stays at **314**, and that is written up in
  `bug_sweep.rs` precisely because it did not move. Three functions left the
  set; three private helpers (`says_for`, `line_for`, `line_for_folder`)
  entered it in the same pass. The ceiling counts every function not reached
  from outside its own module, helpers included, so building a feature out of
  small private pieces holds it flat even when the dead capability it unblocked
  is gone. The named-orphan list is the number that actually moved.
- `tests/guards.rs`: six new entries (`from_folder`, `load_index`, the
  read-back-not-re-derive line, the relief phrase, the intent, plus the
  existing `drift`).

### One side effect, caught in packaging

The first version wrote an index whenever the notes folder existed, empty or
not — so every test in the tree that builds a `Daemon` against the shipped
config wrote `data/index.md` into the repo root, and it turned up inside the
packaged zip. An index of nothing describes nothing and cannot drift, so it
is no longer written at all until there is something to index.
`data/index.md` is in `.gitignore` and in `upgrade::YOURS` regardless: it is
derived from the notes, which makes it about Eric's folder rather than about
Atlas, and losing it on an update would cost a rebuild and hide any drift
that had accumulated.

### What this does not do

- **Per-folder indexes remain a later step.** The module header describes an
  index note in *every* folder and a bullet index at the top of every daily
  note. What exists today is the master index over the notes folder, with
  sub-folders listed as folder lines carrying a count. The count is the most
  that can be said truthfully about a folder that has no index of its own.
- **`needs_splitting` only warns.** Past `MAX_LINES` a rebuild says the index
  is worth splitting into folders. Nothing splits it.
- **No note has ever been read from Eric's real folder.** Every test here runs
  against folders the test built. `data/notes` is empty in this tree, and
  `research` — the only thing that writes notes today — ships off.

## 14. The flight recorder: `trace.rs` wired, and what it says about the rest of the proactive layer

### First, what the rest of the layer is actually blocked on

The proactive track had four things left: `nudge::daypart_with_brief`,
`nudge::convene`, `nudge::offer_to_mend` and `nudge::trace_line`. Reading them
against what feeds them changes the picture:

| | Blocked on | Verdict |
|---|---|---|
| `daypart_with_brief` | an inbox | **blocked on a feature, not a wire** |
| `convene` | a decision Atlas can't settle | needs a ruling |
| `offer_to_mend` | corrections being recorded twice | wireable, `revise.rs` is unwired |
| `trace_line` | "an intent for asking" | **wireable today — done below** |

`daypart_with_brief` is the important one, and it is worth being exact about
why. `brief::run(items, day, cfg)` derives `yours`, `drafted`, `handled`,
`ignored` and `blocking` **entirely from `items`**, which are mail. Only
`conflicts` come from `day`. There is no mail reader anywhere in this tree,
so `daemon.rs` calls it as:

```rust
let b = crate::brief::run(&[], &[], &crate::brief::BriefConfig::default());
```

Empty items, empty commitments, default config — which is `enabled: false`, so
`run` returns immediately anyway. The morning brief is computed over nothing
and always says "Nothing needs you." Attaching `daypart_with_brief` to the
daypart greeting would attach a pipe to an empty tank: wired, green, and still
not a feature. It needs an inbox, and an inbox is an IMAP integration — a real
decision about third-party surface area, not a wiring pass.

Two more call sites have the same shape and are worth knowing about:
`crate::money::summarise(&[])` and `crate::messaging::spoken(&[], ...)` in the
`Intent::Mail` branches. Both are reached; both are handed nothing.

### What was wrong with `trace.rs`

Same shape as `contents.rs`, one module along. `trace.rs` shipped with a
`Call`, a `Trace` that rolls at 5,000, `failure_rate`, `typical_ms` (median,
not mean, "because with a local model on a laptop that stall happens"),
`busiest()`, `caused_corrections()`, `grade_last`, `blame`, `spoken()`, and
`to_line`/`from_lines` describing a file format in detail.

**Nothing ever recorded a call.** No file was written, none was read, and every
reader computed over a `Vec` only a test had filled. The module header gives
four reasons it earns its place — you cannot debug what you cannot see, the
correction loop needs a first time to count, a local model earns trust by
measurement, and without it every prompt change is a vibe — and not one of
them was true of a recorder that recorded nothing.

### The recording

Added to `trace.rs`: `log_path`, `append`, `load`, `compact`, `model_name`.

**`append` never fails the call it is recording.** It returns `bool` rather
than `Result` and the daemon logs a miss once. A flight recorder that can take
the aircraft down is worse than no flight recorder.

**`model_name` reads the name out of the request body it is actually sent in.**
There is no `name` field on `LlmConfig`, and adding one would let the config
disagree with what is on the wire — the same two-declarations-of-one-fact
problem section 2 removed from `settings.rs`. When the body carries no name it
says `unnamed` rather than inventing a label, because a made-up label makes
`typical_ms` average two different models together.

**`compact` writes to a temp file and renames**, so a crash halfway leaves the
old log intact rather than a half-written one.

### Both call sites, not one

There are exactly two places in this program that reach a model: `Brain::decide`
in `run_command`, and `research::run`. Both are recorded, and
`tests/guards.rs` holds both. A flight recorder that misses half the flights is
worse than none, because the half it has looks complete.

Timing is taken at the call site rather than inside `decide`, because what
matters is how long *you* waited — reaching the model and parsing what came
back included — not the part the model spent thinking.

`Reached::NotNeeded` is **not** recorded. That is the phrase parser settling a
question without sending anything, and logging those would make the record say
Atlas asks the model about everything, which is the opposite of what it is for
and would make `busiest()` meaningless.

### The promise, and the test that would notice it breaking

`trace::STORES_NO_CONTENT` says "lengths and timings only; the words of a
prompt are never written to disk". It already had a guard entry. It now has a
test that puts a passphrase into a prompt, runs a real turn against a real
`Llm`, and reads the file back looking for it.

### Asked, and answered

`nudge::trace_line`'s orphan entry named its one missing prerequisite: an
intent for asking. That intent is `Intent::ModelTrace` — phrases in
`config/commands.yaml`, a place in each of the six exhaustive matches,
`AutoProceed` in `policy.rs` and `Need::Local` in `connectivity.rs` (reading a
log Atlas keeps about itself never makes a model call). Plus
`atlas trace [status|failures|compact]`, which breaks the count down per
module — "what is actually using the model" being, per the module header,
never what you expect.

### The bug the tests found, twice

`trace_path()` was `data/logs/model-calls.jsonl`, fixed. Every `Daemon` in the
suite therefore wrote to **one shared file in the repo root**, so two tests
running at once each saw the other's calls — and the repo quietly collected a
log nobody asked for. The second attempt derived it from the store's *parent*,
which for a store at `/tmp/atlas-fr-x` is `/tmp`, so every test shared `/tmp/logs`
instead. It is now `store.root()`: the one directory that is genuinely this
install's, which on a real machine is `data/state` and so is already preserved
by `atlas update`.

This is the same class of mistake as `data/index.md` in section 13 — a path
that looks per-install and is not — found twice in one session, once by a
failing test and once while packaging.

### And a third path bug, found the same way

`atlas trace` read `data/logs/model-calls.jsonl` while the daemon, after the
fix above, wrote into the store. For one commit the command reported an empty
log while the daemon was filling one two folders away — nothing failed, it
just always said nothing had happened. Caught by running the command rather
than by a test, which is why there is now a test: `tests/flight_recorder.rs`
asserts `run_trace` derives its path from the same store the daemon writes to.

That is three path bugs of one kind in one session (`data/index.md`, the
trace log twice, this). The pattern is worth naming: **a path that looks
per-install and is not.** Anything written by a `Daemon` should be derived
from `store.root()`, and anything read by a CLI command should be derived the
same way, or the two drift apart silently.

### Every new guard was watched failing

Thirteen mutations, each reverted: `append` truncating instead of appending, a
failed write reporting success, `from_lines` giving up on the first bad line,
`compact` keeping the oldest, `model_name` inventing a label, the prompt's
words reaching disk, parser-settled calls being logged, a down model recorded
as fine, the record never read back at startup, nothing written at all, the
fixed shared path returning, the asking phrase removed, and asking no longer
reading the record. All thirteen caught.

### Ratchets

- `nudge::trace_line` removed from `ORPHANS`. **Named orphans 10 → 9.**
- `trace::to_line` and `trace::from_lines` removed from `KNOWN`.
- `DEAD_CAPABILITY_CEILING` **314 → 312**, written up in `bug_sweep.rs`: three
  left the set, `daemon::model_in_use` entered it.
- Six new `tests/guards.rs` entries.
- `tests/flight_recorder.rs`: 24 tests.

### What this does not do

- **`grade_last` and `blame` still have no caller.** They are the correction
  loop — tying a bad answer to the exact call that produced it — and they want
  `revise.rs` wired, which is the next honest piece of work here.
- **No real model has been recorded.** Every test drives a fake `Llm`. There
  is no ollama in this container, so `typical_ms` has never measured a real
  local model and the whole point of the thing — "is the 7B good enough" —
  cannot be answered until it runs on Eric's machine for a while.
- **Nothing calls `compact` automatically.** `atlas trace compact` is manual.
  The in-memory `Trace` rolls at `KEEP`; the file does not until asked.

## 15. The brief, redesigned: mail is one source, not the source

### The root cause, and the one under it

Section 14 said the brief was blocked on an inbox. That was true and it was not
the bottom. `brief.rs` had exactly one call site:

```rust
let b = crate::brief::run(&[], &[], &crate::brief::BriefConfig::default());
```

Two empty slices — and `BriefConfig::default()` because **`BriefConfig` was not
a field on `ToolsConfig` at all**. There was nowhere to turn the brief on. Its
default was `enabled: false`, `run` returns at its first line when disabled, so
the morning brief was a function that always returned the same empty answer,
and no amount of finding it inputs would have changed that.

So there were two faults stacked: a config with no switch, and an input type
that could only be email on a machine that is meant to work offline first.

### What changed

**`Source`.** An `Item` now says where it came from: `Mail`, `Handoff`,
`Blocked`, `Job`, `Booking`, `Post`, `Upkeep`. Only `Mail` returns true from
`needs_network()`. Mail keeps its place in the list rather than being removed —
dropping it would make adding a reader a redesign instead of a change at one
line — and `from_mail` still produces exactly what it produced before.

**Each source converts itself**, so a new source is a new function rather than
a change to `run`:

| | comes from | weight |
|---|---|---|
| `from_handoffs` | a friend's note at the door | Info, → Urgent after 48h unanswered |
| `from_backlog` | requests Atlas could not finish | Urgent if waiting on **you**, Info if it clears itself |
| `from_jobs` | scheduled work | failed → Urgent item; due today → a `Commitment` |
| `from_bookings` | a proposed time nobody answered | Urgent — silence becomes a no |
| `from_posts` | a post awaiting your yes | Info, `Outcome::Drafted` |
| `from_upkeep` | a drifted index, a guess worth re-checking | Info — housekeeping never outranks a person |

`gather` composes them; `from_here` runs the brief over the result and adds
`handled_since` — scheduled work that ran and worked since the brief last
looked, which is the "here is what I handled" half. Without that the brief is
only ever a list of demands, which is the accusation the module header is
written against.

**`most_blocking` finally has an input.** It was written to say "X is holding
up 3 other things" and nothing ever set `conflicts_with`. Offline the answer is
the blocker, so three things stuck behind no connection now produce exactly the
sentence it was built for.

**Offline is the ordinary case.** `Sources` carries `online`, and when the
network is down the sources that need one are left out rather than listed and
unactionable. `Reach::Unknown` counts as offline here, the same caution `Reach`
documents for requirement decisions.

**`Item::headline()`.** `"{from} — {subject}"` is right for a person and wrong
for a mechanism — "me — fix the printer" and "a scheduled job — back up" are
both worse than the subject alone. Mail keeps the old shape exactly.

**The config exists now**: `brief` on `ToolsConfig`, a `brief:` section in
`config/tools.yaml`, and `enabled` defaulting to **true** — because the reason
it was off (a brief could only ever be empty) is no longer true.
`draft_replies` stays **false**: there is no mail reader to reply to, and a
drafting promise nothing can keep is worse than no promise.

### Two bugs the redesign exposed

**`draft_replies` was gating the wrong thing.** Its own config comment says
"draft replies at all — off until you have watched it read for a while", which
is a question about whether *the brief may compose*. `run` used it as whether a
draft may be *shown*, and those differ the moment a draft arrives already
written: a post `publish` is holding for your yes was demoted to `Yours` with
its text thrown away. The setting now governs mail — the only source the brief
would ever write for — and a draft that arrived already written is reported.

**`daypart_with_brief` ran the brief twice.** Its first line always said it
took "the day's brief already run"; its signature took raw items and ran one.
Given a caller that had already run a brief to decide whether there was
anything worth greeting about, that meant two runs a tick — and the second was
handed the first one's *output*, so `drafted` was always empty by the time the
relief was read off it and the morning greeting could never offer the one thing
it exists to offer. It takes a `&Brief` now.

### Wired

- `Intent::Outstanding` builds a real brief. The on-screen panel lists the
  brief's items with their source rather than the backlog alone, so the panel
  and the spoken line cannot disagree.
- The daypart greeting carries the run when there is one — and only then. A
  greeting that says "nothing needs you" every morning is the count-shaped
  notification this module is written against, and `Brief::is_empty` already
  knew the difference.
- `Daemon::brief_now`, `upkeep_questions`, and `last_brief` so "I handled 4"
  counts what happened since rather than everything that ever ran.

The doorstep is loaded fresh on each brief rather than held on the daemon: the
server thread writes it when a friend sends something, so a held copy would be
the stale one.

### Every new guard was watched failing

Fourteen mutations, each reverted. Thirteen caught first time. The miss:
reverting `Intent::Outstanding` to the old empty call **left the test green**,
because that reply is the brief followed by `backlog.summary()` and the summary
names the same item — so the test was passing on the tail. It now asserts on
"Start with", which only `brief::spoken` produces. Same class as section 13's
guard-passing-on-its-own-comment: **a test that passes on something adjacent to
what it is testing.**

### The ceiling went up, and that is the ceiling telling on itself

`DEAD_CAPABILITY_CEILING` **312 → 318**. The first increase, recorded rather
than absorbed, because "it may only shrink" is the rule.

Ten new functions, most called from `gather` and nothing outside the module —
the helper bucket, which this ceiling counts. Meanwhile every number that
actually measures backlog moved the right way: named orphans **11 → 9**,
test-only **147 → 143**, and seven functions got production callers across the
session.

The total cannot tell "a capability nothing reaches" from "a small private
helper", so building a feature out of well-named pieces raises it and inlining
them all into one function would lower it. `tests/dead_capabilities.rs` already
computes four buckets with a ceiling on each; those are the numbers worth
ratcheting and this total is worth retiring. **Left in place, because retiring
a ratchet is Eric's call and not a thing to do quietly in the commit where it
first got in the way.**

A correction while counting: earlier revisions of the handover and the task
list said "nine orphans" while the list held eleven — the prose was counting
bullet groups, not names. Both are now measured.

### What this does not do

- **`brief::from_mail`, `vet_draft` and `as_chain` are still orphans**, and now
  they are the *honest* measure of what a mail reader would unlock — three
  functions, not the whole module.
- **`mind::speak_brief` is a second brief.** `Intent::Ready` builds its own
  short list from the publisher and the backlog and speaks that. It overlaps
  what `brief.rs` now does and was left alone: merging them means deciding
  whether the waking line and the morning run are one thing or two, which is a
  design call rather than a wire.
- **`money::summarise(&[])` and `messaging::spoken(&[], ...)`** still have the
  empty-input shape this section removed from the brief. Same fix, same
  question underneath: where does the data come from without a third party.

## 16. The ratchet removed, and what replaced it

Eric's call: if it doesn't work, get rid of it. It didn't, so it's gone.

### How it failed

`DEAD_CAPABILITY_CEILING` was the sum of four groups from
`tests/dead_capabilities.rs`. One of those groups — **helper, also tested**:
its own module calls it and a test covers it — is *live, tested, running code*.

That meant the ceiling went **up by six** when the brief's gathering was
written as ten small well-named functions, and would have come **down** if all
ten were inlined into one unreadable one. A ratchet that rewards the worse
version of the same code is worse than no ratchet, because it gets obeyed.

Second fault, on top: a sum can move for four unrelated reasons and never says
which. Every encounter with it ended in reading a justification comment and
moving the number, which is why the last commit's comment ran to twenty lines.

### What replaced it — three numbers, each meaning one thing

| | measures | held to |
|---|---|---|
| `ORPHANS` | nothing calls it anywhere | **named, one by one**, with a stated reason each |
| `test_only` | only the tests call it — built, proven, never reached | **exact count: 143** |
| `helper_untested` | own module calls it, nothing tests it, `pub` for no visible reason | **exact count: 33** |
| ~~`helper_tested`~~ | — | **nothing, deliberately. This is just code.** |

**Exact, not ranges.** The old values were ranges "so an unrelated commit does
not fail" — and that slack is what let test-only sit at 147 under a ceiling of
160 for weeks while nobody noticed it could have been 143. A number that may
only fall is a ratchet; a number with headroom is a suggestion. Lowering one
now *requires* editing the constant, which is where the reason gets written.

Also removed: `the_number_of_unused_capabilities_does_not_grow` in
`bug_sweep.rs`, which computed deadness by a **second copy** of the same rule.
Two copies in two files is how the two numbers came to disagree. `calls`,
`whole_word` and `after` went with it; `tests/dead_capabilities.rs` is now the
only place that decides what "nothing calls this" means, and the `guards.rs`
entry protecting that rule was repointed there.

### Four mutations, four different guards

A new orphan → caught by the named list. A new test-only capability → caught by
the exact count (144 against 143). A count quietly widened back to 160 → caught.
The summed ceiling reinstated → caught. Each by the guard that should catch it,
which is the thing the single number could never do.

### Two self-reference traps in one test

`the_bucket_that_was_not_measuring_deadness_is_gone` asserts the old constant
is not declared — and it names that constant in its own assertion, so the file
always contained the string it was searching for. First attempt failed on its
own text; second attempt, searching for the fuller `const NAME`, failed the
same way. The needle is now built at runtime from two pieces.

That is the **third** time this session a guard has been confounded by its own
text — after the `commands.yaml` guard passing on the comment that quoted the
phrase it guarded, and the `Intent::Outstanding` test passing on the backlog
summary beside the brief. Worth stating as a rule: **a guard must not be able
to satisfy itself from its own source.**

### Cost

`tests/bug_sweep.rs` 14 tests → 13. The suite is 211 binaries and 4,326 tests.

## 17. The council, convened — about the machine it is running on

Eric's ruling: council runs on **hardware specifics**, with the general
"ask the room about anything" form as the fallback. Both are wired.

### What was wrong

Third module this session with the same shape, after `contents` and `trace`.
`council.rs` shipped complete — five dispositions, blind and open rounds, a
tally that names the split rather than averaging it, a `strongest_dissent` that
can never be empty when there was one, a `suspiciously_unanimous` flag on the
theory that four seats agreeing on the first pass means the question leaked the
answer.

**Nothing ever built an `Opinion`.** `tally`, `Verdict`, `spoken` and
`strongest_dissent` all computed over a `&[Opinion]` only a test had filled,
and `nudge::convene` produced five prompts that nothing sent and nothing read
back. `is_quorate` and `covers_different_ground` — both written to refuse a
room before it costs anything — had never refused anything.

Two things were missing and only one was code.

### The decision half: why hardware

A council's whole value is that every seat looks at **the same real numbers**.
Five seats arguing about "should I upgrade" is five opinions; five seats
arguing about 15.7GB with no discrete graphics is a decision.

Hardware is the subject Atlas *has* measured numbers for — `fit::measure()`
reads what `health` already takes every tick. So `council::hardware_room` hands
every seat the same measured machine, and the dispositions map onto it:

| seat | argues from |
|---|---|
| mover | wants Atlas doing more today |
| sceptic | has watched a machine that benchmarked fine fall over under load |
| operator | pays for the hardware and the power it draws |
| user | has to live with it and only cares what it lets them do |
| steward (ties) | drivers, heat, spare parts, and the second machine that must match |

The briefs carry `fit::describe`, free and total RAM, what Atlas can actually
use right now, the current tier and model — and `fit`'s hard-won note that
**integrated graphics share system memory, so VRAM is not extra**. A seat told
it has video memory it does not have will argue for a model that will not load.

### The code half: reading a seat's answer back

`parse_opinion` is deliberately lenient about shape and strict about
substance. A local model will not reliably return JSON, and demanding it means
throwing away four good answers because one opened with "Sure!".

The one thing it will not do is **invent a lean**. `Seat::prompt` tells every
seat that "a seat that will not commit is an empty chair"; a reply committing
to nothing is recorded as `Depends`, which `tally` counts separately and which
can leave the room with no call at all. That is a real finding, and far better
than a coin flip dressed as a verdict. `empty_chairs` names those seats out
loud.

### The cost, handled rather than hidden

Five seats is **five model calls**. That is why it sat unwired, and it is now
the reason it can be: every call goes through `record_model_call` as
`council`, so `atlas trace` shows exactly what a room cost and `busiest()` will
name it if it starts eating the model budget. Wiring the flight recorder first
is what made this affordable to wire at all.

`Round::Open` — where seats read each other and may revise — is **not run**. It
is a second five calls, and `council`'s own first rule is that Open may only
follow Blind, so stopping after Blind is the design working rather than half of
it. A test asserts it stays that way until someone decides it is worth the
spend.

Other honest edges: a model that is down produces *no verdict* rather than one
built from two answers (`MIN_SEATS` is checked again after the round, since a
seat that could not be reached is left out rather than filled in); an empty
question spends nothing; and with no model at all it says why.

### The bug the tests caught

`parse_opinion` used `has_word` to decide whether "for" was present and
`lower.find(" for ")` to decide *where* — and the second cannot match a reply
that opens with "For". So a seat saying *"For — ship it. The case against is
thermals, which are fine"* was recorded as **Against**: the exact opposite of
what it said, on the most important field in the module.

Two different rules for the same word is how that happens. There is now one,
`word_at`, returning a position, and presence is "did it return one".

### A process failure worth recording

The mutation sweep was killed mid-run by a timeout. It had already applied
mutation #14 — deleting the line that says what the room was looking at — and
died before restoring it. The next run then snapshotted the **already-mutated**
file as its baseline, reported that mutation as "the code has moved", and left
the deletion in the tree.

Caught by re-running the suite afterwards, not by the sweep. The rule:
**a killed mutation run leaves the tree dirty; always re-run the tests before
trusting it.** Fifteen mutations, all fifteen confirmed caught once the tree
was clean again.

### Ratchets

- `nudge::convene` got a production caller. **Exact test-only count 143 → 142**,
  lowered with the reason in the constant — which is the new ratchet working
  exactly as intended: it refused to let the change pass unaccounted.
- Four new `tests/guards.rs` entries, including one on the string `"council"`
  so the cost cannot stop being recorded.
- `tests/a_room_that_disagrees.rs`: 25 tests. Suite: 212 binaries, 4,352 tests.

### What this does not do

- **No real model has convened a room.** Every test drives a fake `Llm`. Five
  sequential calls on a local 7B is a long silence and the real number is
  unknown until it runs on Eric's machine; `atlas trace` is where it will show.
- **`parse_opinion` has never read a real model's prose.** It is built for
  what local models actually do rather than for JSON, but that is a prediction
  until one answers.
- **`reclaimable_mb` is still zero**, so every seat is briefed on a slightly
  pessimistic machine. `fit` says why: Atlas cannot see what memory is held by
  things you are not using, and guessing would inflate the budget.

## 18. The correction loop — and the place a lesson had to live first

### The module, and why wiring it was not enough

`revise.rs` shipped complete: a `Correction` that distinguishes a complaint
from a lesson, a `Mending` that waits for the repeat, `home_for` deciding where
a lesson has to live, `proposal` naming the exact change before making it, and
`repeat_rate` — the one number it says matters.

**Nothing ever built a `Correction`.** `heard` never fired, no `Edit` was ever
produced, `nudge::offer_to_mend` had no caller, `repeat_rate` divided by an
empty list. Fourth module this session with that shape after `contents`,
`trace` and `council`.

But this one could not be fixed by adding a caller, and that is the finding.
Its **rule 1**: *where it is written decides whether it works* — a lesson about
how a task is done has to be somewhere read **every time**, or it is a note in
a diary nobody opens.

`daemon::context()` — everything the model ever sees — was displays, apps, the
focused window, recent files, and the conversation. **Nothing learned.** So
there was nowhere a lesson could live where it would be read again, and filing
one anyway would have produced exactly the failure the module header names:
"Same fact, two places, one of them useless."

### What was built

**`revise::standing`** — the lessons, as the model reads them, and
`context()` now carries it every turn. `Home::HowTo` first and always, because
those are the ones `read_every_time` is true for: if the cap bites it must bite
the preferences, not the instructions. Bounded at `MAX_STANDING` for the same
reason the brief is bounded — a context that grows with every correction
eventually crowds out the thing you just said.

**`wanted_in`** — the fix, taken out of the sentence you said it in. "That was
too long, keep it to one line" carries both halves. "That's wrong" carries one,
so `is_actionable` is false and Atlas asks rather than filing a rule that
forbids one thing and teaches none.

**The flow, end to end.** A correction is recorded whether or not it earns an
edit (a note never promoted is still the evidence for the next one);
`trace::blame` and `grade_last` mark the model call that caused it; a second
correction *on a separate occasion* produces an `Edit`, which is **offered**,
never written silently. Saying yes writes it where `context()` reads it.
`Session::started` separates occasions, so restating a complaint in the same
breath is emphasis rather than a second occasion.

`Intent::HowAmIDoing` reads the scoreboard back.

### Three bugs, one of them a repeat of my own

**The yes-path wrote nothing.** `Intent::ApplyLesson` was graded
`RequireApproval`, so the answer to an offer was *re-gated* and asked for
approval a second time for the same edit. The proposal **is** the approval —
`apply_lesson` has nothing to write unless one was made and shown — so it is
`ProceedAndReport`. Found by a test, not by reading.

**The one-shot CLI path never set `last_said`.** `atlas "that was too long..."`
goes through `execute_timed`, not `turn_from`, so a correction typed at the
command line arrived with no sentence attached and Atlas asked "what did I get
wrong?" about something just said.

**A marker with a leading space cannot match at position 0.** `" next time "`
missed "next time lead with the number" entirely. This is the **second time
this session** — `council::parse_opinion` had it with `" for "`, and a seat
saying "For — ship it" was recorded as Against, the exact opposite of what it
said. The haystack is space-padded now. Worth stating as a rule alongside the
guard one: **a word-boundary marker needs a boundary that exists at position
zero, and the start of the string is one.**

### Why the parser hands over the wrong half

`Intent::GotItWrong` arrives carrying the text *after* the phrase that matched:
"that was too long, keep it to one line" parses to
`GotItWrong("keep it to one line")` — the fix, with the complaint discarded. A
correction needs both, because the complaint is what makes two corrections
match as the same one. Hence `last_said`, set at both entry points, documented
as existing for exactly that reason.

### Ratchets

- `nudge::offer_to_mend` got a production caller. **Exact test-only 142 → 141.**
- Four new `tests/guards.rs` entries, including one on
  `crate::revise::standing` — the line that makes the whole loop mean anything.
- Fifteen mutations, all fifteen caught, on a verified-clean tree this time.
- `tests/telling_it_twice.rs`: 25 tests. Suite: 213 binaries, 4,377 tests.

### What this does not do

- **`Edit::replacing` is always `None`.** Every lesson is an addition; nothing
  yet replaces or retires an earlier line, so two corrections about the same
  thing leave the newer one winning by `applied`'s dedupe rather than by an
  edit that names what it supersedes. `proposal` already has the wording for
  the replacing case and nothing produces one.
- **`stale_notes` still has no caller.** Corrections that never earned an edit
  and have gone quiet are meant to be surfaced for review; nothing surfaces
  them. `upkeep_questions` in the brief is the obvious home.
- **Lessons land in `Mending`, not in `facts`.** `Home` names three
  destinations and all three currently resolve to the same list. Splitting them
  — instructions into the prompt, preferences into `person`, dated facts into
  `facts.rs` — is a real piece of work and would want `facts` to be read into
  context too.
- **No model has ever read a standing instruction.** The lesson reaches
  `context()`, and whether a local 7B actually *obeys* a line in it is
  unmeasured. `repeat_rate` is the number that will say.

## 19. `models` + `gguf`: choosing a model for the machine it is actually on

The biggest strategic item in the tree, and the first whole *module pair* to
come off `UNWIRED_BASELINE` this session.

### What it is

`models.rs` calls itself "the rest of what Ollama does, in Rust": find the
models on disk, read their metadata, work out what fits in memory, format the
prompt the way each model expects, and run `llama-server` directly so there is
one fewer piece of someone else's software in the path. `gguf.rs` is the file
format reader underneath it.

All of it was written and tested. **None of it was ever called.** Nothing
scanned a real folder; `choose`, `best_fit` and `explain` had no production
caller; and `scan_reporting` — which exists precisely so an unreadable folder
is not reported as "no models installed" — had never reported anything to
anyone.

### The root cause was a number in a config file

Every decision was sized against `models.memory_budget_mb`, which the shipped
config set to 3500 under this comment:

> 15.7GB total RAM with Windows already using ~12.8GB. 6GB would fight the OS
> for memory.

That reasoning is correct and writing the number down was still wrong. It is a
**measurement**, and a measurement in a config file stops being true the moment
you close a browser, add a stick of RAM, or run Atlas on the other machine.
`fit.rs` already reads it every tick. The earlier task list had raised "is 3500
or 6000 right?" as a ruling and then withdrawn it as *not a decision* — the
budget should come from the machine. That is now what happens.

`memory_budget_mb: 0` means "whatever this machine can spare". A non-zero value
is a **cap** and may only lower what was measured, never raise it — a budget
larger than the machine produces a model that will not load, which is the
failure `fit.rs` exists to prevent, arrived at from the other side.

### What got wired

- `Daemon::which_model` and `Intent::WhichModel` — scan the real folder, size
  against the measured machine, say what was chosen **and the number it was
  deciding against**. "It used the small one" is only not a mystery if you can
  see the budget.
- `scan_reporting`'s trouble half: a missing folder and an empty one are
  different problems and the old answer sent you to the wrong one.
- `layers_here` — GPU layers from `Machine::usable_vram_mb`, so integrated
  graphics are not counted as spare video memory. Offloading more than fits
  makes the driver page, which is slower than offloading none.
- `is_running` — whether the server is up, asked through the configured fetch
  tool rather than an HTTP client of its own.
- `footprint_mb` — the same estimate `best_fit` sized against, so what Atlas
  says starting it will cost and what it chose by cannot disagree.

### The piece that makes "no Ollama" true rather than merely possible

`ShellLlm` could always talk to `llama-server` — it speaks whatever
`tools.llm.request` says. What it needed was for *you* to hand-write a request
body wrapping the prompt in the exact control tokens that model expects. Get it
wrong and the model still answers, just worse, and nothing tells you.

`models::llm_config_for` builds that connection from the model file itself:
`Template::detect` already knows the wrapping from the GGUF's own chat
template, and `response_path` is `content` (llama.cpp) rather than `response`
(Ollama). `main.rs` uses it when there is no hand-written `tools.llm` and the
models folder has something in it.

**A hand-written `tools.llm` always wins.** If you have written a connection
you mean it, and silently overriding it would be the worst kind of helpful.
There is a test on that precedence, because it is the part that would quietly
do the wrong thing.

### The bug was in my own test fixtures

Two tests failed claiming a cramped machine was given the large model. The code
was right: my fixture declared a "7B" model with **two tensors**, so it weighed
79MB and fitted in 200MB of RAM. Every block now gets its seven real tensors.
A fixture that is wrong in the direction of "everything fits" makes correct
code look broken, and I nearly went looking in `best_fit`.

### Ratchets

- **`UNWIRED_BASELINE` 29 → 27**: `models` and `gguf` both off it. The ceiling
  went **34 → 27**, set to the list's actual length rather than left with
  slack — the slack is what let it drift above reality before.
- Wiring a module un-skips *all* of its functions, so three appeared as orphans
  (`health_url`, `completion_url`, `completion_body`) and one as test-only
  (`footprint_mb`). All four now have callers or direct tests; **no ratchet
  number was raised to accommodate them**, which was the point of making them
  exact.
- Three new `tests/guards.rs` entries, including one on
  `memory_budget_mb: 0` so the measurement cannot be hardcoded again.
- Twelve mutations, all twelve caught.
- `tests/which_model_fits_here.rs`: 23 tests (suite: 214 binaries, 4,400), against **real GGUF bytes written
  to a real folder** — a registry tested against hand-built `Model` structs is
  exactly what existed while the scan had never run.

### What this does not do

- **Nothing starts the server.** `launch` exists and spawns a process; nothing
  calls it, and `lifecycle::Supervisor` — which would own its memory budget and
  reap it when idle — is not involved. That is the next piece, and it is
  genuinely blocked here: there is no `llama-server` binary in this sandbox, so
  a start path could be written but never run.
- **No GGUF file from a real model has been read.** The fixtures are real bytes
  in the real format, hand-built. A file from Hugging Face may carry metadata
  shapes these do not.
- **The derived connection has never reached a server.** The URL, body,
  template and response path are all asserted; whether llama-server accepts
  them is unverified until it runs on Eric's machine.

## 20. Removing the repetition, including the copy I was about to add

Eric's standing rule: repetitive things that cause confusion, aren't needed, or
cause inefficiency, and can be fixed another way — go.

### What was actually repeated

Wiring `models` cost an extra full run because it had to be deleted from **two**
not-yet-wired lists and the second failure only appeared after the first was
green. Three files keep such a list. The obvious read is "three lists, collapse
them" — and that read is wrong, which `capability_wiring.rs` says in its own
code:

```rust
// A module with no public types at all is a bag of functions —
// `wiring.rs` already covers whether anything calls it.
if types.is_empty() { continue; }
```

They check three different things: does anything **name** the module
(`wiring.rs`); is what the module is **for** reached, a borrowed helper not
counting (`capability_wiring.rs`); and which individual **functions** have no
caller (`new_capabilities_are_wired.rs`). Merging the lists would either
over-exempt — a module excused from the strict check gets excused from the weak
one — or need a scope marker per entry, which is three lists wearing one name.

Measured, not assumed: the two module lists share 25 entries, and the 5 that
differ are each correct for their own check.

### The copy I was about to add

I wrote a test that read all three lists and worked out for itself whether each
entry was stale. **It reported eleven modules stale that are not**, on its first
run, and was deleted before it ever passed.

Of course it did. "Is this module wired" is a *rule*, and that rule already
lives in the two files that need it — `wiring.rs` strips config-only references
because a module named solely as a `ToolsConfig` field is not wired, and

## 21. An idle tick went from 26 filesystem operations to zero

Efficiency pass over the running system, not the tests. Measured throughout —
two of the three things I went looking at turned out not to be worth touching,
and saying so is the useful half.

### Measured and left alone

**`tools_cfg()` deep-clones a 162-field config**, at 51 call sites, and one
clone costs **21.5µs**. That looks bad until you count what actually fires: a
thread-local counter through a real `turn` and a real `tick` says **2 per turn,
1 per tick**. The other 49 sites are inside intent branches that do not run.
~43µs a turn is not worth a refactor that would touch fifty call sites.

**`onlyone.rs` writes a heartbeat file unconditionally** — and must, because
its content is the current time. Content-comparing that one would skip every
write and break the lock.

### The real one

`daemon::persist()` saves **thirteen** subsystems after every turn and every
tick. Each save was a write *and* a rename — **26 filesystem operations** — and
on a normal tick none of the thirteen had changed. You asked what was
outstanding; the modes, the flows, the watcher, the anticipator and the rest
were exactly as they were.

`Store::save` now compares the serialised bytes against the file and returns
early when they match.

| | before | after |
|---|---|---|
| `persist()` | 1032µs | **133µs** |
| writes per idle tick | 13 (+13 renames) | **0** (13 skipped) |
| writes per turn | 13 | **3** (session, thread, journal — the ones that changed) |

What is left of the 133µs is the serialising, which has to happen to know
whether anything changed at all.

### Why compared against the file, not a remembered hash

A hash held in the `Store` would be faster still. `Store` is `Clone` and holds
nothing but a path, so two stores can point at one directory — `main.rs` makes
more than one — and a hash remembered in one would be wrong about what the
other wrote. It would also be wrong about a file deleted underneath it. The
file cannot be wrong about either.

Dirty flags were the other option and are worse for the same reason in a
different shape: a flag someone forgets to set is data silently not saved.
Content comparison cannot lose anything — if the bytes differ it writes, if the
file is missing it writes, and the temp-then-rename atomicity on the path that
writes is untouched.

### Checked before, not after

The one way this could have removed a capability is if something read the
**mtime** of a state file to decide that something changed. Every `modified()`
in the tree reads notes, indexed user files, reclaim candidates or model files.
Nothing reads `data/state/*.json` mtimes. `reclaim` takes its roots as an
argument rather than discovering them, which is why.

`tests/writing_only_what_changed.rs` — 8 tests, each about something that must
**still** happen: a changed value writes, a partial change writes, a deleted
file is restored, two stores on one directory do not shadow each other, the
first save creates the directory, the write that does happen is still atomic,
and a real `Daemon` still keeps its backlog and scheduler across a restart.
Five mutations, all five caught.

### Not chased

`tick()` is ~2.1ms in debug and only 133µs of that is disk now. The rest is
compute, and I stopped rather than keep digging — there is no evidence yet that
it matters, and the measurement to justify the next change would want a real
machine rather than this container.

## 22. `mend`: "I'll wait" was a promise nothing kept

Next off the unwired list. Picked because it is one of the few remaining that
is pure logic — most of the other 26 need a phone, a second machine, a
microphone, editing software or a Windows desktop.

### What was wrong, and it was not a missing caller

`mend.rs`'s second half is about **asking someone who does not read code**: a
`Question` that knows how to be phrased, how to check it is answerable without
jargon, how to read out loud, and what backlog item it becomes.

Nothing ever built one. So `Blocker::NeedsYourDecision` — the one backlog
variant meaning "Atlas found something only you can settle" — was produced by
exactly one function, `Question::parked()`, and that function had no caller.
The variant existed, `explain()` described it, `self_clearing()` knew it does
not clear on its own, the brief surfaces it, and **nothing in the program could
create one**.

The missing piece was noticing the daemon already had the moment this is for
and dropped it on the floor:

```rust
Decision::RequireApproval => {
    if self.autonomy == Autonomy::Unattended {
        "That needs your say-so. I'll wait.".into()
    }
```

Nothing waited. No record anywhere, so the next time you looked there was no
trace you had been asked. **A promise Atlas does not keep is worse than a
refusal.**

And `daemon::called` had been sitting there since the same night carrying the
note *"not yet called from anywhere — `mend`'s question-parking flow is not
wired into the daemon loop tonight"*, with an `#[allow(dead_code)]` on it. Both
are gone; the compiler will say so if it ever stops having a caller again.

### What it does now

`park_for_you` enforces the three things `mend` already knew:

- **Answerable without reading code**, or it is not asked at all — a question
  Atlas cannot phrase is one it does not understand well enough to be asking,
  and burying that in a backlog item would hide the real problem.
- **A real choice** — one option is an announcement, four is asking you to
  design rather than decide.
- **Nothing guessed meanwhile** — one thing set aside, the rest carries on.
  Silence costs you a parked task rather than a night built on a wrong
  assumption.

It lands as a `NeedsYourDecision` item, which the brief already surfaces, and
does not clear because you came back — being at the machine is not a decision.

### Two things deleted rather than kept

**`about_ambiguity`, which I wrote in this same pass.** The moment is real —
`Decision::AskClarification` parks its question in the *session*, which
evaporates if you walk away, exactly like the approval branch did. But the
daemon has one clarification sentence, not two readings. Building the question
would have meant **inventing the options**, and a choice between two things
Atlas made up is worse than being asked to rephrase. It went; the moment is in
the outstanding list instead.

**My own redundant `backlog.save`.** `run_command` persists at the end of the
turn and `Drop` persists on the way out. A third call would be a third
declaration of when state is written — and since section 21, `Store::save`
skips unchanged content, so it would usually have written nothing while looking
like the thing keeping the question alive.

### Bugs found, including in my own work

`plainer` — which strips the things only a programmer says out of a request —
**trimmed the punctuation off each word and then looked for it**, so
`cleanup()` had its parentheses removed and sailed through. It also lost a
space, producing "deletethat".

Then the mutation sweep found **four misses, and three were my tests asserting
a proxy**:

- The end-to-end case called `park_for_you` directly, so reverting the daemon
  branch to the old "I'll wait" left everything green. Same shape as the brief
  test that passed on the backlog summary beside it. There is now a test that
  drives a real turn.
- The phrasing tests went through `answerable_without_code` instead of looking
  at the sentence — **which hid a real gap**: `NEEDS_CODE` catches `.rs`, `()`
  and `::`, but a bare path with no extension contains none of those, so the
  check passes on a question with a filesystem path in it. The tests now assert
  the produced sentence.

Nine mutations, all nine caught after that.

### An existing test that was right to fail

`unattended_atlas_says_it_will_wait_rather_than_acting` asserted
`reply.contains("wait")` — it was asserting the *promise*. Its second
assertion was the one that mattered and still holds: no question is parked in
the **session**, because that is the one nobody will hear. It now also asserts
the request was set aside, which is what makes "I'll wait" true rather than a
form of words.

### Ratchets

- `mend` off **both** module lists; `UNWIRED_BASELINE` **27 → 26**, ceiling with
  it. The cross-reference added in section 20 worked: the first failure named
  the other list, so both deletions happened in one change.
- Test-only **141 → 142**, raised deliberately: un-skipping a module counts all
  its functions, and `mend::worth_trying` — the paper-over refusal — is blocked
  on the `selfwork::run_tests` ruling. Named in `KNOWN` with that reason.
- Two new `tests/guards.rs` entries.
- `tests/a_question_that_survives_you_leaving.rs`: 12 tests.

### What this does not do

- **The paper-over half is untouched.** `Proposed`, `Cheat`, `paper_overs`,
  `refusal` and `worth_trying` judge whether a proposed fix to code is a fix at
  all — which means Atlas fixing its own code, which is the `selfwork` ruling
  you have not given.
- **`AskClarification` still evaporates when you are away.** Same hole, and it
  needs the daemon to produce two readings it does not currently have.
- **No question has been parked by a real failure.** Every test drives it
  deliberately. Whether the moments that hit `RequireApproval` unattended are
  the ones worth parking is unmeasured until it runs on your machine.

## 23. "If it passes, it gets fixed then and there" — the last four words

I had this wrong in section 22 and Eric corrected it. The boundary is not
"may Atlas run its own tests" — that was never the question, and the test
machinery exists precisely so it can. The boundary is **fix versus
improvement**:

- **A fault**: Atlas identifies faulty code, works out a fix in a sandbox, and
  if it passes it is **fixed then and there** — provided the fix does not
  change or limit what Atlas can do.
- **A gap**: no fault, but Atlas notices it is lacking. That is scoped as a
  build plan, the gaps in the plan are looked for, the plan is improved, and
  it is **put to you to decide on** — the same shape as this conversation.

Every piece of that already existed, and the missing parts were both at the
very end.

### 1. `Next::Land` did not land

`sandbox::plan` calls itself "the preview" in its own doc, and that was the
whole story — **nothing ever applied a `Change`**. `pipeline::Next::Land`
carries a sentence describing what would change in behaviour, and the daemon
printed the sentence. Confirmed by grep: nothing anywhere copied a change's
`source` to its `target`.

### 2. The session was a state machine with no state

```rust
let session = crate::selfwork::Session::new(what, 0);
```

Built fresh on every `WorkOnYourself`. So `stage` was always `Thought` and
`thought` always `None`; it answered "Thought next." forever and could not
reach Build, let alone Implement. `Work` was not even `Serialize`, so it could
not have been kept.

Both are fixed: `Work` and `Session` serialise, the daemon holds one and
persists it, and the same goal resumes where it got to rather than restarting.

### The gate — your constraint, made mechanical

`selfwork::what_holds_it_back` runs four checks before anything reaches the
tree. Every one reports, rather than stopping at the first: three problems
learned one round at a time is three rounds, and the second and third are
usually the informative ones.

| check | why |
|---|---|
| `may_edit` on every path | Atlas may never edit the file that decides what Atlas may edit |
| `Change::target_was` | nothing lands over an edit you made meanwhile — its own doc says overnight work makes the gap hours wide |
| `mend::paper_overs` | **this is "does not change or limit what Atlas can do"** |
| `pipeline::review` blockers | the fix was somewhere other than the cause, or a test was weakened |

The third is the answer to what paper-over needed: a deleted test, a silenced
warning or a widened type makes the check pass and **removes the thing that
would have noticed**. That is limiting what Atlas can do, stated as a diff.

It is not a duplicate of the review. The review counts tests and checks
location; `paper_overs` reads the shapes in the text. `#[ignore]` leaves the
count unchanged, so a review that only counts passes it.

When it lands, the previous version of each file goes to
`data/state/landed-over/` first. A fix Atlas made on its own has to be
something you can put back without asking it.

### A bug the tests caught in the gate itself

`sandbox::plan` produces **absolute** targets; `may_edit` reads
**project-relative** paths and its allowlist is `["src/", "tests/", ...]`. My
first version passed `c.target` straight in, so every change — including a
genuine fix — was refused as "not in the parts of the project I work on". It
strips the project root now, and a target outside the project has no relative
form and is refused for that reason instead.

Found because a test expected a good change to land. A test that only checked
refusals would have passed.

### Two process failures worth recording

**A killed mutation run left the tree dirty again** — the timeout fired mid-run
with `std::fs::copy` deleted from `land`, and the next sweep reported the
anchor missing rather than the mutation. Same lesson as section 17, and this
time the fix is in the method: every mutation now restores in a `finally`.

**My own comment reintroduced the bug it was explaining.** `retrospective.rs`
finds test bodies by splitting on the test attribute, and my fixture contained
a literal one — so the body was truncated before its assertion and the guard
reported a test that asserts nothing. I rebuilt the fixture at runtime so it is
data rather than code, and *wrote a comment explaining the trap that contained
the trap*. The guard caught it twice.

### Ratchets

- Eleven mutations on the gate, all eleven caught.
- Three new `tests/guards.rs` entries.
- `tests/fixing_itself_then_and_there.rs`: 14 tests.
- Suite: 213 binaries, 4,255 tests.

### What this does not do — and what it now needs

- **`self_work.enabled` and `pipeline.enabled` both ship `false`.** Nothing
  runs until they are on, which is correct for something that writes to the
  tree, but it means the gate has never refused a real change.
- **Nothing fills the stages.** `Stage::Thought` needs a theory and a proving
  test; `Stage::Build` needs a change written into the sandbox. Both need a
  model, and there is no llama-server here. The pipeline can now *hold* its
  place between turns; it cannot yet *advance* on its own.
- **`pending_landing` is never populated.** The gate is tested directly. The
  step that runs the tests in the sandbox and turns a pass into a planned set
  of changes is the next piece, and it is the one that wants a real toolchain.
- **Path B is not built.** `Step::Propose { summary }` exists — "it works,
  explain what will be different in behaviour, not in code, and wait" — and
  nothing produces a build plan, looks for its gaps, or puts it to you.
