## The path was already designed; this proves it and pins the assets

`main.rs::model_connection` already builds the local model connection itself:
`Registry::scan(models/)` picks the largest GGUF that fits the RAM budget,
reads that file's chat template, and `models::llm_config_for` wires a curl call
to a llama.cpp `llama-server` on `127.0.0.1:<port>/completion`, reading the
reply at JSON path `content`. So the install is a llama-server + a GGUF + one
config block — no hand-written model connection.

What was missing was proof against a live model (the old `ShellLlm` tests say
"the behaviour needs a running server") and pinned assets. Both delivered.

## Proven here, against a real model

A real Qwen2.5-0.5B-Instruct GGUF was served on the exact two endpoints Atlas
uses (`/health`, `/completion`, llama.cpp's shape) and the tree's **own** code
path was run against it end to end:

- `Registry::scan` → `choose_for` picked `qwen2.5-0.5b-instruct-q4_k_m`.
- `llm_config_for` built the curl→/completion config (response_path `content`).
- `ShellLlm::complete("what is 2+2?")` → **"2+2 equals 4."**
- `explain::in_plain_english("fn add(a,b){a+b}")` →
  **"This function takes two integers, adds them together, and returns the sum."**

So `explain`, `build_it`, the council and the decide loop — all already wired
to the primitive — run against a real local model. Their capability state
stays "Untested" only until the model runs on *your* hardware; the seam,
config-builder, and a real consumer are proven.

- `tools-yaml-models-block.example` — the exact `models:` block, with the
  correct note that `models::launch` appends `-m/-c/--port/--host/-ngl/--no-webui`
  itself, so `server.args` holds only extra flags.
- `serve_reference.py` — the test harness that speaks the two endpoints, for
  understanding/verifying without llama.cpp. (On a real machine, llama.cpp's
  `llama-server` serves the same two; Atlas can't tell the difference.)

cap); both are one pinned/linked download in the bundle.
